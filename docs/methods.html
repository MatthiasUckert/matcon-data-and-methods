The methods

How the contracts were classified and their entities extracted, how to apply the published classifiers and the extraction image, and how to turn the published spans into variables. Each method comes with an example on the sample.

Every example on this page reads the sample in the sample/ folder of the site’s repository: 214 rows of the contracts table. Of these, 180 are labelled contracts, 15 from each of the 12 detailed categories; 3 are attachments the text screen rejected; and 31 are the registrant copies of 3 attachments whose filing names more than one registrant. The sample illustrates the file structure; it is not representative of the corpus.

Classification

Each contract carries three labels, each from a fine-tuned Legal-BERT model (nlpaueb/legal-bert-base-uncased) of its own: a detailed category out of 12, a broad category out of 7, and whether the document is an original contract or an amendment. A model reads the first 256 or the first 512 tokens of a document and ignores the rest. Each task was trained at both lengths, which makes the 6 models of the classifiers part.

The paper’s contract type is Class, the detailed category from the model ClassDetailed_L256, and its broad type is ClassRollup, the roll-up of Class to the broad categories. ClassBroad comes from an additional model trained on the broad labels directly; where it differs from the roll-up, HierConsistent is FALSE.

Cross-validation over five folds of the labelled contracts selected a configuration for each task; for the broad task it selected the 512-token model. The published labels come from the 256-token models in all three tasks.

Applying a classifier

The classifiers part holds the 6 models as zip archives, one per task and context length. All start from Legal-BERT and were trained on the 4,398 labelled contracts in core/Labels.parquet.

Archive Task Categories Context Labelled the published data
ClassDetailed_L256.zip Contract type (Class) 12 256 tokens yes
ClassDetailed_L512.zip Contract type 12 512 tokens no
ClassBroad_L256.zip Broad type from a separate model (ClassBroad) 7 256 tokens yes
ClassBroad_L512.zip Broad type from a separate model 7 512 tokens no
AmendType_L256.zip Original or amendment (AmendType) 2 256 tokens yes
AmendType_L512.zip Original or amendment 2 512 tokens no

Beside the archives, models_index.csv maps each archive to the folder it unpacks to, and deployed.parquet records the configuration cross-validation selected for each task, with its macro-F1. README.md in the same folder is the usage guide; this section repeats it.

What an archive holds. Each archive unpacks to one folder named after the training run; the name spells out the context length (L), epochs (E), batch size (B), learning rate (LR), class weights (W1 on, W0 off) and seed (S). Inside it:

<Task>__nlpaueb-legal-bert-base-uncased__TText_L<len>_E<epochs>_B32_LR<rate>_W<weights>_S42__FINAL/
  model/            the model: config.json with the label mapping (id2label), the weights
                    (model.safetensors) and the tokenizer (tokenizer.json, vocab.txt, ...)
  config.json       the training run: data, labels, hyperparameters, software versions
  train_log.parquet the training loss per epoch
  run.log           the run's log

Running a model. The models were trained with Python 3.12, PyTorch 2.10 and transformers 4.49; recent versions of both libraries load them. A GPU helps but is not needed.

pip install torch transformers pandas pyarrow
unzip ClassDetailed_L256.zip
import pandas as pd
import torch
from transformers import AutoModelForSequenceClassification, AutoTokenizer

model_dir = "ClassDetailed__nlpaueb-legal-bert-base-uncased__TText_L256_E6_B32_LR2e-05_W1_S42__FINAL/model"
max_len = 256                      # the context length the model was trained with: L256 or L512

tok = AutoTokenizer.from_pretrained(model_dir)
model = AutoModelForSequenceClassification.from_pretrained(model_dir).eval()
id2label = {int(k): v for k, v in model.config.id2label.items()}

docs = pd.read_parquet("text/exhibit10/exhibit10_2012.parquet", columns=["DocID", "TextRaw"]).head(32)
enc = tok(docs["TextRaw"].fillna("").tolist(), truncation=True, max_length=max_len,
          padding="max_length", return_tensors="pt")
with torch.inference_mode():
    probs = torch.softmax(model(**enc).logits, dim=-1)
top = probs.topk(2, dim=-1)

docs["Label"] = [id2label[i] for i in top.indices[:, 0].tolist()]
docs["Prob"] = top.values[:, 0].tolist()
docs["Label2"] = [id2label[i] for i in top.indices[:, 1].tolist()]
docs["Prob2"] = top.values[:, 1].tolist()

Three rules the published labels follow. Your own use should follow them too:

  • The input is TextRaw from the documents part, the document’s full text, unchanged.
  • The model reads the first max_len tokens and ignores the rest (truncation=True). Use the length in the archive’s name; a 256-token model given 512 tokens is not the model that was scored.
  • The label mapping travels with the model (id2label in model/config.json); never rebuild it from a list of category names.

Label, Prob, Label2 and Prob2 correspond to BertClassDetailed, BertClassDetailedProb, BertClassDetailed2 and BertClassDetailed2Prob in the contracts table, and likewise for the other two tasks. The documents part holds exactly the text the models read, so a 256-token model run on it reproduces those columns, up to the last digits of a probability that differ between processors.

Rolling up. To roll a detailed label up to the broad category the paper uses (ClassRollup): take the part before the colon, with Customer / Supplier and R&D rolling up to Purchases and Sales, and Leases, Licenses and Other standing alone. The taxonomy table above shows every pair.

The models are derived from Legal-BERT, published under CC BY-SA 4.0, and are published under the same licence.

The keyword classifier

Beside each transformer label the contracts table carries a label from a keyword classifier, an independent second instrument. The core part publishes its lexicon as KeywordTerms.parquet: 160 rows, one per task, category and term, with Task naming the task (ClassDetailed, ClassBroad or AmendType). Term is the keyword, one to three lower-case words searched in the first 256 words of a document. Precision is the share of the labelled documents containing it that belong to its category, and Power, the term’s strength, is the lower bound of the Wilson interval of that precision. The codebook lists the other columns.

The package publishes the terms and the labels they gave; the code that finds a term in a text is in the pipeline (see the Code page). In the contracts table the keyword label of the detailed task is KwClassDetailed, with the keyword that decided it in KwClassDetailedTerm and its Power in KwClassDetailedPower; the label is missing where no keyword applied or two categories tied. The broad task has the same three columns. ClassDetailedFlag and ClassBroadFlag say whether the keyword label confirmed the transformer, contradicted it, or left it unchecked by giving no category. For the amendment task KwAmendType is Amended where an amendment term applies and Original otherwise. The lexicon also lists 12 terms for Original, which that rule does not use.

Extraction

The organisation candidates come from LexNLP 2.3.0, run inside the container image of the extraction image part; places, dates, law clauses and redaction markers come from the pipeline’s own extractors. Rules written in R, part of the pipeline, decide which candidates become spans: they match organisations to the registrant and give each party a role, attach places to parties, read the jurisdiction a law clause names, and place each date relative to the filing date. Running the extraction image says how to apply the image to documents of your own.

Span file One row per
org_mentions mention of a party; one row without a span for a contract with none
places_geo place named, attached to a party or not
law_clauses law clause
date_spans date that could be read
term_spans stated period, or a clause stating the contract has no fixed length
redact_spans redaction or omission marker

Beside each span the files keep what the rules read: whether a place was attached to a party, whether a date falls before or after the filing, whether a period is left open, whether a marker withholds text. From spans to variables turns one span file into a column of the contracts table.

The span files of the sample

Each span file holds one row per entity found, keyed on the document and located by its offsets into the text (see the data page). Counted per document:

Show code 
per_document <- function(kind) {
  start <- grep(
    "Start$",              # the first ...Start column is the span's own start
    names(spans[[kind]]),  # the columns of this span file
    value = TRUE           # the name rather than its position
  )[1]
  spans[[kind]] |>
    dplyr::filter(!is.na(.data[[start]])) |>
    dplyr::count(
      DocID,         # one count per document
      name = "Rows"  # the rows of this kind in the document
    ) |>
    dplyr::summarise(
      Kind = kind,                   # the span file
      Documents = dplyr::n(),        # documents with at least one span
      Spans = sum(Rows),             # spans in all
      Median = stats::median(Rows),  # spans in the typical document
      Max = max(Rows)                # spans in the busiest document
    )
}

Running the extraction image

contracts-lexnlp-17a366b025fe.tar.gz in the extraction image part is the Docker image that extracted the organisation candidates of the database: LexNLP 2.3.0 in Python 3.8, with the NLTK data it needs baked in, so it runs offline. The rules that turn candidates into the published parties are part of the pipeline, not of the image. README.md beside the image is the usage guide; this section repeats it.

Loading it.

docker load -i contracts-lexnlp-17a366b025fe.tar.gz     # restores the image as contracts-lexnlp:latest

The image is built for 64-bit ARM (linux/arm64, native on Apple Silicon). On an Intel or AMD machine Docker runs it under emulation, which works but is several times slower. To run natively there, rebuild it from the Dockerfile in the pipeline repository (material-contracts, folder contracts-lexnlp/, at commit e3f97216ef96d58d6001faf23bc2e5017eed5b7a) and pin its packages to the requirements.lock.txt published beside the image; a rebuild is the same software, not the same image.

Running it. The image reads parquet files with a DocID and a TextRaw column, which is what the documents part holds, and writes one parquet file with one row per match:

docker run --rm -v "$PWD":/work contracts-lexnlp:latest \
  exhibit10_2012.parquet \
  --output lexnlp_org_2012.parquet \
  --label ORG \
  --n-process 8
Option Default Meaning
inputs one or more parquet files or folders, relative to the mounted directory
--output the parquet file to write
--label ORG what to extract: ORG, DATE, GPE, MONEY, AMOUNT, PERCENT, RATIO, DURATION
--id-col, --text-col DocID, TextRaw the input columns
--timeout 60 seconds per extractor and document; past it, the document keeps its other rows
--max-chars 0 (off) read only the first N characters of each document
--n-process 1 worker processes; 0 or less uses all cores

The output has DocID, Start, Stop, Span, Label, LabelRaw, Engine and Model, plus columns specific to each label (for ORG: Name, NameAbbr, TypeFull, TypeAbbr, TypeLabel, Description). Offsets follow the same rule as the published spans: TextRaw[Start:Stop] == Span. A document without any match appears once, with empty offsets, so every input document is accounted for.

The database used the image for ORG only; its places, dates, law clauses and redaction markers come from the pipeline’s own extractors. The documents part holds exactly the text the image read. The wrapper that runs LexNLP is inside the image at /app/extract_lexnlp.py and in the pipeline repository in contracts-lexnlp/ at the commit above.

From spans to variables

TermYears in the contracts table is the longest term the contract states, in years. A contract can state several periods, and term_spans keeps every one of them, with the period in years (TermYears), the phrasing that matched (TermKind) and whether the clause states the contract has no fixed length (IsOpen).       LongestStated,  # the published rule, recomputed

The published column is one rule over the spans. PeriodKind records what each period governs, from the word before it; its codebook adds: “Descriptive only; no variable uses it.” A study that wants the agreement’s own term rather than the longest stated period filters on it and writes its rule in a line.

The span files are keyed on the primary copy of each attachment; HashDocument in the contracts table reaches the other registrant copies.
