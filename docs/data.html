The data

The parts of the data package, the tables of the database, their codebooks, and the conventions of the tables.

The data package v1.0.0 has 5 parts: 123 files, 49.5 GB in all, plus a README and a checksum manifest at the root of the package. Each part is a folder that can be downloaded on its own. The parts are shared from Google Drive, each with its own download link; the whole package has a link of its own.

Every example on this site reads the sample in the sample/ folder of the site’s repository. The sample holds 180 contracts of the labelled sample, 15 from each of the 12 detailed categories; 3 attachments the text screen rejected; and all 31 registrant copies of 3 attachments filed by several registrants, so that the conventions below can be shown. That is 214 rows of the contracts table, with the rows every other table and span file holds for them. The examples run from the root of a clone of the repository and need the R packages arrow, dplyr, stringi and tibble; none needs the data package.

The parts

The database

One row per registrant copy of an Exhibit 10 attachment with its filing, classification and content variables, the announcement, place, term and confidential treatment tables beside it, the codebooks, the contract index, the labelled sample and the keyword terms.

  • 424 MB in 16 files
  • Published: download

Entity spans

The entity spans the rules kept, with their position in the document and the properties the rules read: organisation mentions, places, governing-law clauses, dates, terms and redaction marks.

  • 1.1 GB in 7 files
  • Published: download

The documents

The retrieved documents themselves, as filed and as text: Exhibit 10 attachments, the current reports (8-K and 8-K/A) that announced a material agreement, and the confidential treatment orders, split by type and filing year.

  • 45.3 GB in 86 files
  • Published: download

The classifiers

The six fine-tuned models, one archive per task and context length, with the index that maps them to the training runs, the record of which configuration cross-validation selected, and a usage guide.

  • 2.44 GB in 9 files
  • Published: download

The extraction image

The container image that extracted the organisation candidates, with its lockfile, a licence notice and a usage guide.

  • 317 MB in 4 files
  • Published: download

Reading the files

The tables are parquet files:

  • R: arrow::read_parquet("core/Contracts.parquet")
  • Python: pandas.read_parquet("core/Contracts.parquet")
  • SQL: duckdb -c "SELECT count(*) FROM 'core/Contracts.parquet'"
  • Stata: StataNow reads parquet with import parquet; other editions convert a table with R (haven::write_dta()) or Python (pandas.DataFrame.to_stata()) first, using the StataName column of the codebooks.

No .dta files are published.

The sample keeps the package’s folders, file names and columns, so an example moves to the package by replacing sample/ with the root of the package. The documents are the exception. The sample keeps them in one file, text/exhibit10/exhibit10_sample.parquet, where the package has one file per type and filing year, text/<type>/<type>_<year>.parquet. The sample holds Exhibit 10 attachments only, without the HTML column, the document as retrieved from EDGAR. It carries no contract index, no models and no extraction image.

A file too large for memory is opened lazily and filtered before it is collected:

Show code 
exhibits <- arrow::open_dataset("sample/text/exhibit10")  # a folder of parquet files, opened as one table
wanted <- arrow::read_parquet(
  "sample/core/Contracts.parquet",  # the contracts table
  col_select = "DocID"              # only the key is needed here
)$DocID[1]                          # one document of the sample

exhibits |>
  dplyr::filter(DocID %in% wanted) |>  # the documents a study needs
  dplyr::select(
    DocID,  # the document
    YQ,     # its filing year and quarter
    DocExt  # its file type as filed
  ) |>
  dplyr::collect()  # the rows are read here

The tables of the core part

The core part holds the tables below with their codebooks, the contract index, the labelled sample and the keyword terms. The column meanings shown are taken from the codebooks.

Contracts

One row per registrant copy of an Exhibit 10 attachment: 1,462,939 rows, of which the sample holds 214. The filing, the classification and the content variables of the contract sit side by side; below are its keys, the filing, the rejection and copy flags, the labels and the sample flags:

Column Meaning
DocID One registrant’s copy of an Exhibit 10 attachment: the registrant’s CIK and a hash of the attachment, joined by a hyphen. Unique in this table and the key every other table joins on.
HashDocument Hash of the attachment’s content. Shared by all registrant copies of one document, so it groups the copies of one contract.
HashIndex The filing that carried the attachment. Joins to Summaries (the filing’s announcement) and CtoOrders.
CIK The registrant’s Central Index Key on EDGAR. With DateFiled, the key for matching other databases.
UrlDocument Address of the attachment on EDGAR.
FormType The form the attachment was filed with: 8-K, 10-K, 10-Q, S-1 and so on.
DateFiled The day EDGAR accepted the filing.
Removed TRUE where the attachment failed the screen for usable text (reason in RemClass). These attachments stay in the table, flagged, so that what was set aside remains visible.
RemClass Why the attachment was set aside: too short, not prose, mostly digits, or no readable text.
MultFiler 1 where the filing names more than one registrant, so that the attachment appears once per registrant.
PrimaryFiler 1 on the one copy of each attachment the entity variables were computed from; the other copies carry the same values. Count contracts on PrimaryFiler == 1.
DescSample 1 where the attachment is in the paper’s descriptive sample.
EstiSample 1 where the attachment is in the paper’s estimation sample, which requires a Compustat match on CIK and filing date. The matched Compustat data are not published.
Class Contract type, twelve categories: the label the paper uses.
ClassRollup Broad contract type, seven categories: the broad category of Class, as the paper uses it. The part of Class before the colon; Customer / Supplier and R&D roll up to Purchases and Sales; Leases, Licenses and Other stand alone.
ClassBroad Broad contract type from the additional broad classifier (see BertClassBroad). Where it differs from ClassRollup, HierConsistent is FALSE.
AmendType Original or Amended: the label the paper uses.

EstiSample marks the paper’s estimation sample, which requires a Compustat match; Compustat is not published (what needs WRDS).

Summaries

One row per current report (Form 8-K or 8-K/A) with an Item 1.01 text announcing a material agreement: 278,997 rows. SumAttached is 1 where the filing carried an Exhibit 10 and 0 where the agreement was announced without the contract. The sample holds the 59 announcements that carried a sampled contract.

Column Meaning
HashIndex The 8-K filing. Joins to Contracts where the filing carried a contract.
DocID The 8-K document the Item 1.01 text was read from; its text is in text/8k or text/8ka.
DateFiled The day EDGAR accepted the filing.
SumAttached 1 where the filing carried an Exhibit 10; 0 where the agreement was announced without the contract.
SumDates Distinct agreement dates at the start of the Item 1.01 text: a proxy for the number of agreements announced.
SumDateFirst The first of those dates: the agreement date.
SumLagDays DateFiled minus SumDateFirst, in calendar days; negative where the filing precedes the date. Item 1.01 allows four business days.
SumWords Words in the Item 1.01 text, without its heading and title.
SumBoiler Share of the text’s four-word phrases that occur in the filings of at least one in a hundred distinct filers (after Lang and Stice-Lawrence 2015).

Places

One row per contract, geographic level (country, state, county or city) with its state and country, party role and law-clause flag, with the number of mentions: 9,545,088 rows, 1,862 in the sample. The table does not name cities or counties; spans/places_geo.parquet (GeoUnit) names them. GeoCountry keeps the country’s name as found in the text, so one country can take several rows in a contract; count countries on GeoCountryIso. Like TermDocs below, the table holds the primary copy of each attachment (PrimaryFiler == 1); HashDocument reaches every registrant copy.

Column Meaning
DocID The contract (its primary copy). Joins to Contracts on DocID.
HashDocument The attachment; joins to every registrant copy in Contracts.
GeoLevel What the place name resolved to: Country, State, County or City.
GeoState The US state, where the place gives one.
GeoCountryIso ISO 3166 alpha-3 country code; USA for US places. Count countries on this column.
GeoCountry The country’s name as found in the text. One country can appear under several spellings, including other languages.
PartyRole The party the place was attached to: registrant, cofiler, counterparty, signatory, other, or none.
InLawClause 1 where the place sits in a governing-law clause, so it is a jurisdiction rather than a location.
nMentions How often the contract mentions this place in this role.

TermDocs

One row per contract and term family, 5 families, on the primary copy of the contract: 5,949,025 rows, 930 in the sample. HashDocument reaches the other registrant copies.

Column Meaning
DocID The contract (its primary copy). Joins to Contracts on DocID.
HashDocument The attachment; joins to every registrant copy in Contracts.
Family The term family searched for: Pandemic, Disruption, RateReform, Regulation or Boilerplate.
nHits Occurrences of any term of the family; a term found twice counts twice.
nTerms Distinct terms of the family found.
HasTerm 1 where nHits is positive.
FirstPos Relative position of the first hit: 0 at the start of the text, 1 at its end.
PerKWords nHits per thousand words of the contract.

CtoOrders

One row per exhibit reference in a confidential treatment order, whatever the order decided (Status) and whether or not it was linked to a contract (LinkStatus): 32,410 rows. The sample holds the 17 references linked to a sampled contract.

Column Meaning
OrderDocID The order’s own document on EDGAR; its text is in text/cto.
OrderDate The day the order was filed.
Status GRANTING, DENYING or REVOKING, as the order’s title states.
IsExtension 1 where the order extends an earlier grant.
ExhibitNo The exhibit number the order names, such as 10.1.
ReleaseDate When the granted treatment ends.
DocID The contract the reference was resolved to. Joins to Contracts on DocID.
LinkStatus A-linked where the order was linked to a contract; otherwise the numbered step at which linking failed (1 no reference read, 2 not an Exhibit 10, 3 source filing not named, 4 filing not on EDGAR, 5 filing ambiguous, 6 no exhibit retrieved from that filing, 7 exhibit ambiguous, 8 lettered exhibit number, 9 exhibit not among those retrieved).

The contract index, the labelled sample and the keyword terms

ContractIndex.csv.gz locates each contract on EDGAR, keyed on DocID: the filing (AccessionNumber, CIK, CompanyName, FormType, DateFiled), the attachment within it (DocName, DocSeq, DocDesc), its labels and the two EDGAR links; its codebook below lists every column. It is a compressed CSV, so it opens without a parquet reader.

Labels.parquet is the labelled sample: one row per labelled contract with the reference labels and the cross-validation fold in which it was held out (Fold), 4,398 rows, of which the sample holds 180.

KeywordTerms.parquet holds the keyword terms of all three classification tasks, 160 rows, with Task naming the task a term belongs to. It is described with the keyword classifier.

The codebooks

Every table in core/ has a codebook beside it (*_Codebook.csv), one row per column with its type and meaning. The span files share one codebook, whose File column names the file a row describes, and the documents in text/ have their own. The sample holds the codebooks where the package does. Every column keeps its name in Stata. The search box above each codebook filters its rows.

Conventions of the tables

Three conventions matter for any count. The examples below start from the contracts table of the sample:

Show code 
contracts <- arrow::read_parquet("sample/core/Contracts.parquet")  # core/Contracts.parquet in the package

The unit of observation is the registrant copy

One row of the contracts table is one registrant’s copy of one Exhibit 10 attachment. When a filing names two registrants, the same attachment arrives twice, once under each registrant’s CIK. HashDocument identifies the attachment itself and is shared by its copies; DocID identifies the copy. DocID is the registrant’s CIK and the hash of the attachment joined by a hyphen, as the check below confirms; the accession number sits in UrlIndexPage and, under its own name, in the contract index.

Show code 
contracts |>
  dplyr::summarise(
    Rows = dplyr::n(),                              # copies in the sample
    Attachments = dplyr::n_distinct(HashDocument),  # distinct documents among them
    DocIDIsCikAndHash = all(  # TRUE when every key is the CIK and the hash, not the accession number
      DocID == paste(
        CIK,           # the registrant
        HashDocument,  # the attachment
        sep = "-"      # joined as in the published key
      )
    )
  )
Rows Attachments DocIDIsCikAndHash

Rejected attachments stay in the file

Removed marks an attachment that failed the screen for usable text, and RemClass gives the reason. These attachments stay in the table, flagged, so that every retrieved attachment is accounted for; an analysis of readable contracts filters on Removed.

Show code 
contracts |>

    Removed,  # TRUE where the attachment failed the screen for usable text
    RemClass  # why it was set aside

The sample carries 3 such attachments, so the count above gives their reasons and the filter below drops them:

The two filters together leave 183 of the 214 rows of the sample: one readable contract each.

Span offsets are 0-based and half-open

Every span file locates its entity with a start and a stop offset into the published text of the document. The offsets are 0-based and half-open, and they count characters, not bytes. In R the span is stringi::stri_sub(TextRaw, Start + 1, Stop); in Python it is text[Start:Stop].

Show code 
options(arrow.use_altrep = FALSE)  # plain R strings, so a text joined to many spans is not converted for each
text <- arrow::read_parquet("sample/text/exhibit10/exhibit10_sample.parquet")
dates <- arrow::read_parquet("sample/spans/date_spans.parquet")

dates |>
  utils::head(8) |>
  dplyr::inner_join(
    text,         # the published text the offsets point into
    by = "DocID"  # a span file and the text share the document key
  ) |>
  dplyr::transmute(
    DocID,                       # the document
    DateStart,                   # 0-based start
    DateStop,                    # half-open stop
    Sliced = stringi::stri_sub(  # what the offsets cut out of the text
      TextRaw,                   # the published text of the document
      DateStart + 1,             # a 0-based start is R's 1-based first character
      DateStop                   # a half-open stop is R's inclusive last character
    ),
    DateText                     # what the span file stores
  )

The same holds for every span file. Each names its offsets after its entity (DateStart, MentionStart, …) and most store the text they found beside them; the governing-law file stores none.

Show code 
offset_check <- function(file) {
  spans <- arrow::read_parquet(file) |>
    dplyr::inner_join(
      text,         # the published text the offsets point into
      by = "DocID"  # a span file and the text share the document key
    )
  start <- grep(
    "Start$",      # the first ...Start column is the span's own start
    names(spans),  # the columns of this span file
    value = TRUE   # the name rather than its position
  )[1]
  end <- sub(
    "Start$",  # DateStart, MentionStart, ...
    "Stop",    # ... pair with DateStop, MentionStop, ...
    start      # the start column found above
  )
  stored <- grep(
    "Text$",       # DateText, PlaceText, SpanText, ...: the text the extractor stored
    names(spans),  # the columns of this span file
    value = TRUE   # the name rather than its position
  )[1]
  sliced <- stringi::stri_sub(
    spans$TextRaw,       # the published text of each span's document
    spans[[start]] + 1,  # 0-based start to R's 1-based first character
    spans[[end]]         # half-open stop is R's inclusive last character
  )
  tibble::tibble(
    File = basename(file),                    # the span file
    Rows = nrow(spans),                       # rows in the sample
    WithOffsets = sum(!is.na(sliced)),        # rows that locate a span
    Stored = stored,                          # the column holding the stored text, if any
    SliceEqualsStored = if (is.na(stored)) {  # spans whose slice is the stored text
      NA_integer_
    } else {
      sum(
        sliced == spans[[stored]],  # slice and stored text agree
        na.rm = TRUE                # a row without offsets has nothing to compare
      )
    }
  )
}

Counting characters matters. Curly quotes, section signs and bullets take more than one byte each, and a tool that slices bytes cuts the wrong text for every span after the first of them:

Show code 
first_wide <- text |>
  dplyr::transmute(
    DocID,                                         # the document
    FirstWide = stringi::stri_locate_first_regex(  # where byte and character positions first part
      TextRaw,                                     # the published text
      "[^\\u0000-\\u007f]"                         # the first character outside ASCII
    )[, "start"]
  )

dates |>
  dplyr::left_join(
    first_wide,   # each document's first character outside ASCII
    by = "DocID"  # one position per document
  ) |>
  dplyr::summarise(
    Spans = dplyr::n(),        # date spans in the sample
    AfterWideCharacter = sum(  # spans a tool that slices bytes would cut wrongly
      DateStart >= FirstWide,  # the span starts after a character of more than one byte
      na.rm = TRUE             # a document without such a character shifts nothing
    )
  )
Spans AfterWideCharacter
1644 1203

180 of the 214 documents in the sample contain such a character.

In Python the slice is the same once the text is a str. PlaceStart and LawStart are stored as doubles, and pandas reads the offsets of org_mentions as floats because its rows without a span have none; dropping those rows and casting with int() makes the block work on every span file:

import pandas as pd

text = pd.read_parquet("sample/text/exhibit10/exhibit10_sample.parquet").set_index("DocID")["TextRaw"]
dates = pd.read_parquet("sample/spans/date_spans.parquet").dropna(subset=["DateStart"])

dates["Sliced"] = [
    text[doc][int(start):int(stop)]  # 0-based and half-open: Python's own slice
    for doc, start, stop in zip(
        dates["DocID"],       # the document
        dates["DateStart"],   # 0-based start
        dates["DateStop"],    # half-open stop
    )
]

Known issues

The package’s README lists these issues of v1.0.0; the figures below come from the sample.

  • Columbia. The gazetteer reads “Columbia” as the country Colombia, so Colombia is heavily over-counted in Places, places_geo and the country counts of Contracts; in US contracts the word is almost always the District of Columbia, British Columbia or a US city. In the sample, 25 rows of places_geo read “Columbia” as Colombia.
  • Country spellings. A country can appear under several names, some in other languages; count on GeoCountryIso. In the Places table of the sample, USA appears as “United States”, “United States Of America”, “Usa”.
  • Durations. DurationYears is left missing above 30 years (DurationDropped says so); other date columns are not capped.
  • Broad label. The paper’s broad category is ClassRollup. ClassBroad comes from an additional model trained on the broad labels directly; HierConsistent marks where the two differ (classification).
  • Span offsets. LawStart and PlaceStart are stored as whole-numbered doubles, the other offsets as integers.
  • Parties. A contract without any identified organisation has one row in org_mentions without a span (above).
  • No document-level gold set exists for the entities. The labelled sample in Labels.parquet covers the classification, not the extraction.
  • The text as read. TextRaw is exactly the text the classifiers and extractors read. In some HTML documents, quotation marks, apostrophes and dashes appear as control characters (U+0080 to U+009F): they were written in Windows-1252 and read as Latin-1. The package’s README gives a repair in R and in Python that swaps one character for one, so every offset stays valid. A model or extractor run on repaired text reads slightly different input from the one that produced the data.

Not in the package

  • Compustat. It is licensed. EstiSample marks the rows of the paper’s estimation sample; the match to Compustat can be rebuilt from CIK and DateFiled (what needs WRDS).
  • Amounts. Monetary amounts were extracted but are not used by the paper and are not published.

Checking a download

MANIFEST.sha256 at the root of the package lists every file with its SHA-256 checksum. Google Drive may deliver a large folder as several zip files; unpack them into one folder, with MANIFEST.sha256 at its root, before checking. From that folder (macOS, Linux), the first line checks the whole package and the second only the parts its pattern names, here core and spans:

shasum -a 256 -c MANIFEST.sha256
grep -E '  (core|spans)/' MANIFEST.sha256 | shasum -a 256 -c
